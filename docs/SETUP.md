# Setup

From a fresh clone to a running app, and exactly which values enable cloud
accounts.

## 1. Guest mode (no configuration)

```bash
git clone https://github.com/tiwariraman884/studySprint.git
cd studySprint
npm ci
npm run dev
```

Open http://127.0.0.1:3000. Everything works as a guest: the planner, subjects,
materials, questions, quizzes, revision, priority view, coding lab, assistant,
themes and backups. Progress lives in this browser.

The account panel states that cloud accounts are not configured and keeps
"Continue as guest" working. Nothing is hidden and nothing pretends to save.

## 2. Environment variables

The app reads configuration from the **server process environment** at startup.
The server injects only the two public values into the page; the rest never
leave the server.

### Where to set them

| Environment | Where | Notes |
| --- | --- | --- |
| Local development | A file named `.env.local` in the repository root, or shell variables before `npm run dev` | `.env.local` is git-ignored and read by the dev server at startup. A real environment variable always wins over the file, so CI and hosting are unaffected |
| CI | Repository Settings → Secrets and variables → Actions | Only the public two are ever needed in CI; the database job starts its own PostgreSQL |
| Hosted deployment | Your host's environment-variable settings (for example a Cloudflare Worker secret/variable) | Variables are read per request, so a redeploy is not needed after changing a value |

### The variables

| Variable | Public? | Required for | What it is |
| --- | --- | --- | --- |
| `SUPABASE_URL` | **Public** | Account sign-in, cloud sync, guest import | Project URL, `https://<project-ref>.supabase.co`. Dashboard → Project Settings → API |
| `SUPABASE_PUBLISHABLE_KEY` | **Public** | Account sign-in, cloud sync, guest import | The publishable key (`sb_publishable_…`) from Project Settings → API. The legacy `anon` key is also accepted via `SUPABASE_ANON_KEY` |
| `SUPABASE_SERVICE_ROLE_KEY` | **Secret** | Only the content importer (`POST /api/packs/import`) | Service-role key. Used by the server alone and never injected into a page |
| `IMPORT_TOKEN` | **Secret** | Only the content importer | A long random string the importer requires in the `x-import-token` header. Without it the importer refuses to run |
| `SITE_URL` | Public | Correct redirect URLs and cross-origin checks | The origin students use, e.g. `https://study.example`. Defaults to the bound address locally |

The two public values are safe in the browser: they identify the project and are
protected by row-level security. **Never** put the service-role key in a
`PUBLIC_` variable; `npm run check` and `npm run build` refuse to proceed if a
service-role key looks like it is being used as a client key, and the build
scans the output for secret patterns.

### PowerShell, this session

```powershell
$env:SUPABASE_URL = "https://<project-ref>.supabase.co"
$env:SUPABASE_PUBLISHABLE_KEY = "sb_publishable_..."
npm run dev
```

The dev server prints at startup whether cloud accounts are configured.

## 3. Apply the database migrations

Use the Supabase CLI against your project (or a local stack):

```bash
supabase link --project-ref <project-ref>
supabase db push                 # applies supabase/migrations/*
supabase db reset                # local: re-applies migrations and the seed
```

Or apply them by hand to any PostgreSQL 15+ database:

```bash
for f in supabase/migrations/*.sql; do psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f "$f"; done
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 \
  -c "select public.import_course_pack(p.pack, p.\"contentHash\") from jsonb_to_recordset('[]'::jsonb) as p" 2>/dev/null || true
# The repeatable way to import the pack is the importer (below) or the seed file.
```

The migrations are idempotent enough to re-run on a fresh database; the seed is
endlessly idempotent (it checks the content hash).

## Auth behaviour of a fresh Supabase project

A newly created project has an email sign-up rate limit on its built-in sender
(roughly a handful of messages per hour) and rejects reserved domains such as
`example.com` with `email_address_invalid`. Both are reported honestly in the
account panel:

- **Email rate limited** — the project answered HTTP 429. Wait for the window to
  pass, or configure SMTP (see [Authentication](AUTHENTICATION.md)), which removes
  the built-in limit.
- **Address rejected** — use a real, deliverable mailbox.

To test a whole sign-up flow repeatedly while the built-in sender is limited,
either configure SMTP, or temporarily turn off "Confirm email" in
Authentication → Providers → Email (then the account is usable immediately and
no message is sent; turn it back on before inviting real students).

## 4. Seed the course pack

The authored content is compiled into `supabase/seed/10-course-packs.json`
(generated by `npm run seed:packs`; CI fails if it is stale). Import it either:

- **through the app's importer** (recommended for a hosted project):

  ```bash
  node -e "const d=require('./supabase/seed/10-course-packs.json')" # inspect first
  curl -X POST https://your-app.example/api/packs/import \
    -H "content-type: application/json" -H "x-import-token: $IMPORT_TOKEN" \
    --data-binary @supabase/seed/10-course-packs.json
  ```

  The importer calls `public.import_course_pack`, which is service-role only.
  Re-importing identical content changes nothing.

- **or** through psql, running `supabase/seed/20-import-course-packs.sql` with
  the JSON file mounted at `/tmp/seed/10-course-packs.json`.

## 5. Configure the auth redirect URLs

Add both to Supabase → Authentication → URL Configuration → Redirect URLs:

```
http://127.0.0.1:3000/auth/callback
http://127.0.0.1:3000/auth/reset
https://<your-domain>/auth/callback
https://<your-domain>/auth/reset
```

Set **Site URL** to the origin students use (`https://<your-domain>` or
`http://127.0.0.1:3000` locally). Details and the email settings are in
[Authentication](AUTHENTICATION.md).

## 6. Verify

```bash
npm run verify      # syntax, 65 unit tests, smoke, build
npm run test:pg     # needs Docker or STUDY_SPRINT_PG=supabase + SUPABASE_DB_URL
```

`npm run test:pg` with no Docker daemon will report that PostgreSQL integration
could not start. Set `STUDY_SPRINT_REQUIRE_PG=1` to make that a failure, which is
what CI does.

## 7. First run as a student

1. Open the app. As a guest you are offered a short four-step setup: you, your
   subjects, your time, review.
2. Finish it, and the dashboard opens on a real first session.
3. Choose **Account → Sign in or create an account** to create an account.
   Confirm the email, then sign in.
4. Choose **Account → Import guest progress** to review what you did as a guest
   before anything is uploaded.
